# Every sub-app also runs standalone

A sub-app generated by Flightdeck Studio mounts in Flightdeck OS **and** runs
on its own. Not a port, not a second build — the same files, with the host's
side of the contract supplied by a small harness.

```sh
npx tsx packages/codegen/src/cli.ts \
  --spec fixtures/wc-clock.spec.json \
  --out ../flightdeck \          # the host tree: 7 files + a registry patch
  --standalone ./wc-clock-alone  # the same 7 files + the harness
```

```sh
cd wc-clock-alone && npm install && npm run dev
```

`npm run standalone` from this repo does the whole thing end to end and says
whether it worked.

## What "the same files" means, exactly

The sub-app's own files are emitted **once** and written to both roots. A test
hashes every one of them and fails on a single differing byte, because a
"standalone build" that forks the page is not the app running standalone — it
is a second app that drifts, and it drifts silently.

| | host tree | standalone tree |
|---|---|---|
| `server/subapps/<id>/**` | ✅ | ✅ byte-identical |
| `web/src/subapps/<id>/index.tsx` | ✅ | ✅ byte-identical |
| `tests/subapps/<id>/**` | ✅ | ✅ byte-identical |
| `server/subapps/registry.ts.patch` | ✅ (a human applies it) | — |
| `standalone/**` + shims | ⛔ never | ✅ |

## The coupling, and how it was actually found

A generated sub-app reaches the host through a small number of imports. The
first version of this harness supplied **two** of them, on the reasoning that
reading the emitted page showed the whole coupling. It did not:

```
round 1  ../../capabilities.js          CapabilityDeniedError, at runtime
round 2  ../../lib/flightdeckAudit.js   the guard's audited refusal
round 3  ../installRow.js, ../killSwitch.js, ../../project/types.js,
         ../../workspace/types.js
round 4  ./registry.js (server-side), ../../db.js
```

Four rounds of `MODULE_NOT_FOUND`, each found by **booting it**. Then four more
gaps found by **typechecking it**, which is a different question again — the
app served HTTP 200 while `req.workspace`, `req.project` and `req.principal`
were type errors against stock Fastify, and one of my own shims had a
`string | undefined` bug. Running is not compiling.

So the coverage check does not read a list anybody maintains. It reads the
imports the emitted files **actually contain** and requires each to resolve
inside the standalone tree. Removing any one shim fails it by name.

## What is different, and what deliberately is not

| | Flightdeck OS | standalone |
|---|---|---|
| Capability adapter | the workspace's live install row | `standalone/capabilities.ts`, backed by `./data` |
| Enablement layer 1 (`SUBAPP_<ID>_ENABLED`) | ✅ | ✅ **the same code**, verbatim |
| Enablement layers 2–3 (ceiling row, project row) | ✅ | ⛔ absent — reported as `absentLayers`, never as granted |
| RBAC by workspace role | ✅ | ⛔ one local operator |
| Audit | append-only, replicated, read by governance | `data/audit.jsonl`, local, unsigned |
| Inbox | a person resolves proposals | files under `data/memory/proposals/` |
| **Capability scope check** | ✅ | ✅ **not** among the differences |

Two of those rows are the whole point.

**The scope check is real.** `capabilities.ts` throws if a route calls a method
whose scope the manifest does not declare — and it throws
`CapabilityDeniedError`, the class the emitted routes already catch, so a
refusal is a 403 in both modes rather than a 403 in one and a 500 in the other.
A local build that is laxer than the host teaches the app habits the host will
later refuse.

**The enablement gate is not stubbed.** The tempting shim is `enabled: true`.
That does not stand in for consent, it deletes the gate — and an app developed
against a deleted gate meets the real one for the first time in production. So
layer 1 runs for real (it is a `process.env` read with no dependency, copied
verbatim), and layers 2 and 3 come back **false** with `absentLayers` naming
them. An operator who has not set the env var gets a refusal that says why.

The server also refuses to start without `--allow-anonymous`. That flag is the
acknowledgement that the middle column above is not present.

## Why the harness is never applied to a host checkout

Two shims sit at host paths — `server/subapps/registry.ts` and
`server/subapps/types.ts` — and would overwrite the real registry, every other
sub-app with it. So:

- `planWrites` defaults to the **host** target and drops every `standalone` file.
- `applyGeneratedFiles` with `target: "both"` is **refused by name**, not
  skipped. A silent skip is how you find out later that half a harness landed.
- The Studio bundle carries the host half only. The host's own admission rule
  (`ADM-020`, "a path outside the sub-app's own directories") already refuses
  the harness, and that rule is correct. The wrong fix would have been a second
  file list on the bundle that admission does not check — an unchecked region
  carried inside a checked one.

## The four layers that check this, and what each can see

| layer | can see | cannot see |
|---|---|---|
| `codegen/__tests__/standalone.test.ts` | shape, import coverage, byte-identity, class coverage | whether any of it runs |
| `tsc -p standalone/tsconfig.json` | type errors in the tree that ships | whether it starts |
| `standalone-smoke.sh` | boot, the gate refusing, HTTP, the bundle building | whether the page renders |
| `standalone-smoke.mjs` (Chromium) | the DOM, applied CSS, console errors | — |

Each one has caught something the one above it could not. The browser layer
earns its place: with `.card` still *defined* in `theme.css` but made inert,
all 21 text assertions pass and only the browser reports
`.card has no border-radius — theme.css is not applied`.
